- [~] HITL & **Windows Hello** (focus-safe modal; HIGH-RISK biometric); **sensitive-site lockout** (bank/crypto/password/health) — _**sensitive-site lockout: done and enforced.** `policy-kernel.ts` denies every side-effecting call on a bank/crypto/password/health origin and downgrades reads to `ask`, and it is the PEP `ToolGateway` actually calls, so it is live rather than a decision layer. **HITL audit: fixed.** The gateway emitted ONE audit entry, before the prompt — the trail said "we asked" and never "the answer", for exactly the destructive and financial calls where the answer is the record you would want. It now emits the resolution too, and records `biometricRequired` / `biometricVerified`, so a high-risk action approved with a fingerprint is distinguishable from one approved by clicking OK. A `BiometricVerifier` seam exists and an INSTALLED verifier is binding — its refusal overrides a clicked yes, because an authenticator whose no can be ignored is decoration._ — _**owed: Windows Hello itself.** Unimplemented, and the approval modal already says so in en+tr. It needs a native module or a WinRT bridge — a platform-toolchain dependency, deliberately not re-added right after removing the last one. Until then policy asks for a biometric the machine cannot provide, the action still proceeds on a clicked approval, and the journal now says exactly that instead of recording it as verified._
- [x] Scoped Trust Profiles + **Permission Debug** (reason codes) — _**Permission Debug: done.** The reason codes were well chosen and completely invisible: `PolicyResult.reason` was a bare `string`, and the approval modal printed it, so someone stopped by the injection guard read `tainted_side_effect` and had to guess. It is now a closed union (`policy-reasons.ts`), so a new rule does not compile until its code is catalogued, and a parity test fails until that code has en+tr text answering three questions: what happened, why, and what you can do. The modal shows those and keeps the raw code in small print so support can still name it exactly; an unknown code degrades to the bare identifier rather than an empty box. **The union immediately caught a second instance**: the Egress Firewall's HITL request was building its reason by template (`egress_possible_secret:${kinds}`) — not stable, not lookupable — so the kinds moved into `args` where they belong and that path got an explanation too._ — _**Scoped Trust Profiles: done.** The scoping primitives (`plan-grants`, `remembered-grants`) were both the same shape — permission given in REPLY to a prompt, scoped to a run or a skill. What was missing was the other direction: a standing posture the user sets in advance, visible as a list instead of reconstructed from a history of clicks. `trust-profile.ts` adds three levels (`trusted`/`default`/`restricted`) with one invariant enforced in code rather than trusted to callers: **a profile can only ever tighten.** A `deny` stays a `deny`, so nothing in Settings can unlock the sensitive-site lockout; `destructive` and `financial` keep their prompt on every site; and tainted arguments keep theirs, because the trust was placed in a SITE and taint means the values came from that site's own content. The test states that as a matrix over every level×risk×taint combination rather than one example. It is applied at the PEP itself (`PolicyKernel.evaluate` → `withTrust`), not as a layer beside it, so there is no path that reaches a decision without it; it is persisted (migration 14, sync-meta from day 0, soft delete so a revocation can propagate); it is loaded into the kernel at startup before any tab exists; and it has a Settings surface under Privacy that states the ceiling next to the list — "trusted" reads to most people as "anything goes", and a screen that lets someone believe that has mis-set their expectations even when the code behind it is right. A DB row that fails `safeParse` is dropped, which falls back to `default`: a corrupt row can lose a `restricted` setting but can never manufacture a `trusted` one._
